# Changelog

All notable changes to `barometer_flutter` will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). A version does not by itself establish implementation conformance, platform support, field validation, or support for a Draft Barometer specification.

## [Unreleased]

### Added

- Emulator evidence for durability, a full disk and the nine registered measurements. Instrumented tests `DurabilityDeviceTest` (with the test service `DurabilityService` in its own process: a pending bundle, replay records and run-ledger entries survive a process kill during an active attempt) and `StorageFullDeviceTest` (on a filled data partition a new task is not admitted, an admitted one starts no run, stored records are unchanged, and clearing still removes every record, the Keystore key and the sentinel). The example's measurement integration test `integration_test/measurements_test.dart` runs TCP-01, DNS-01, DNS-03, DNS-04, TLS-01, HTTP-01, NET-01, NET-03 and NET-05 from Dart as synthetic embedded tasks from `example/barometer-fixtures/`, selected with the Gradle property `barometerExampleAssets=barometer-fixtures`, against host fixtures that `scripts/android-measurement-fixtures.sh` starts (`scripts/measurement_fixtures.py`, a CA generated per run as the emulator's only trust root, and a packet-filter redirect of the fixture address to the host); without `--dart-define=BAROMETER_MEASUREMENT_FIXTURES=true` it is skipped. `scripts/android-trust-scenario.sh` accepts another synthetic CA through `BAROMETER_TRUST_CA`. `FlowReport` in the example gains `outcome`, which the page does not show. Results on API 24 and 35 emulators, in the standalone and the umbrella build, are in [the Android validation record](docs/android-validation.md#durability-full-disk-and-the-nine-measurements). No Dart API or channel contract change.
- Android host policy adapter (`HostPolicy`). The channel host reads the trusted local document through it at every `initialize`, from the application asset that the host's native code registers with the new `BarometerFlutterPlugin.setTrustAsset(path)` (default `barometer/trust.json`; never from Dart). A document that differs from the active one is a policy replacement, activated only by reinitialization: its `policy_generation` must be strictly greater than every generation activated in the process and the facade must accept it while the active client stays open; the active client is then closed, which cancels its runs and invalidates its handles and deliveries, and a new client over the same record store is initialized. A lower or equal generation with other content fails with `policy_rejected` and an unreadable or invalid document with `trust_invalid`, both leaving the active policy, runs and handles in place. The generation floor is kept in memory for the process, not persisted. The Dart API and the channel contract are unchanged.
- Instrumented tests `PolicyReplacementDeviceTest` (the host rows of the local policy lifecycle through the channel), `LocalPolicyDeviceTest` (the trusted document's `device` constraints against the battery state set with `dumpsys battery`, and its `network_context` eligibility on the proxy path), `ProxyDeviceTest` (`SetProxy` and `ClearProxy` against loopback proxies, `proxy_rejected`, and `cleanup_incomplete` while the record store is held) and `RemoteTaskDeviceTest` (a signed remote package accepted through `InstallRemoteTask`, and a wrong key, altered task bytes and an expired key rejected as `task_source_unauthenticated`), with the test helpers `AnsweringProxy`, `ChannelCaller` and `TestSigner`, an RFC 8032 Ed25519 signer over keys from fixed public test seeds. Host test `HostPolicyTest`. Results on API 24 and 35 emulators are in [the Android validation record](docs/android-validation.md#host-policy-proxy-and-signed-remote-tasks).
- Android network signals: `AndroidNetwork` reports VPN (`detected` or `not_detected` from the application's default network; before API 23 `detected` only when the active network is a VPN and `unknown` when another VPN exists), validation and captive portal (`yes` or `no` from API 23) and suspension (`suspended` in device idle from API 23, on a network without `NOT_SUSPENDED` from API 28 or one blocked for the application from API 29, otherwise `active`; `unknown` before API 23 and until the blocked status is reported). Each change advances the access generation and fires a pending watch; a device-idle receiver joins the network callback, and on API 21 and 22 the callback also follows VPN networks. Backgrounding is not suspension. The access state still holds no identifier.
- Android linkage keys: `AndroidLinkageKeys` implements the facade's `LinkageKeyStore` from API 23 with a non-exportable HMAC-SHA-256 key per storage scope in Android Keystore, created on first use, and a reinstall sentinel in the scope's `no_backup` directory; a key without the sentinel is deleted before use, and deletion removes the key and then the sentinel and creates nothing. `BarometerBinding.newClient` installs it, so `clearMeasurementData` deletes both; before API 23 it is not installed and linkage stays disabled. No StrongBox requirement and no new dependency.
- Instrumented tests `NetworkSignalDeviceTest` (test VPN service, airplane mode, Wi-Fi, forced device idle), `LinkageKeysDeviceTest`, `ClearDataDeviceTest` (the native rows of the clear-data contract), `LifecycleDeviceTest` (engine detach, process kill during an attempt) and `ClearStorageDeviceTest`, with the scripts `scripts/android-airplane-check.sh` (airplane mode from the host on every API level) and `scripts/android-clear-storage-check.sh` (Settings "Clear storage" through `pm clear`, with a control run). Results on API 21, 24 and 35 emulators are in [the Android validation record](docs/android-validation.md).
- `TrustRootDeviceTest`, an instrumented test of the Go library's Android trust-root set in the application process: TLS-01 directly to `8.8.8.8:443` (`dns.google`) and through an in-process loopback CONNECT proxy that answers with a leaf from a synthetic test CA, with expectations per emulator scenario. `scripts/android-trust-scenario.sh` prepares the scenarios on an emulator as root (the synthetic CA as a user-installed CA, or the updatable or system store replaced by a bind mount) and refuses non-emulator devices. The trusted-document and task builders of the instrumented tests move to `DeviceTestDocuments`. Results on API 24 and 35 emulators are in [the Android validation record](docs/android-validation.md).
- Umbrella mode: the plugin can compile against the `barometermobile` facade inside a host application's gomobile umbrella artifact instead of its own library, and then ships no native library and no second gomobile runtime. On Android the Gradle property `barometerUmbrellaArtifact` names the umbrella AAR's Maven coordinates, which the plugin uses with `compileOnly`; on iOS the new `Umbrella` podspec subspec, made the default by `BAROMETER_FLUTTER_UMBRELLA_POD` and `BAROMETER_FLUTTER_UMBRELLA_MODULE`, depends on the pod that vendors the umbrella framework and imports the facade through a small Clang module, and requires static linkage. Standalone mode stays the default and is now the `Standalone` subspec. Only the iOS import in `BarometerBinding.swift` is conditional; the Kotlin and Swift glue is otherwise unchanged. The example builds in both modes, standing in for the host with a local Maven repository and a local pod; the README documents both modes. CI also builds the example in umbrella mode, with the standalone library standing in for the umbrella artifact; umbrella-mode tests ran locally only. No Dart API or channel contract change.
- Example application: pressing a button runs the synthetic embedded TCP-01 or DNS-01 task from Dart through `BarometerClient` (initialize, admit, start, poll `runState`, read and acknowledge the bundle); nothing runs at launch. The synthetic trusted local document and tasks live in `example/barometer/`; the Android build and the iOS Runner build fill their expiry and task-identifier placeholders at build time, because an embedded task must expire within seven days of acceptance. The example manifest requests `INTERNET`. A Flutter integration test runs both tasks, and CI runs it on an Android emulator and an iOS simulator. No Dart API, channel contract or plugin change.
- Apple method channel: `BarometerFlutterPlugin.swift` registers the `com.tvrain.barometer_flutter/client` handler, and `BarometerHost.swift` implements the channel contract with the same arguments, results and error codes as the Android handler. Registration does no work; the host creates the record store and facade client at `initialize`, closes them at `close` or when the engine detaches, and runs every facade call on a worker queue of at most four concurrent operations, never on the main thread. Native code reads embedded tasks from the bundle resource `barometer/tasks/<name>.json` and installs them with the trusted local document's embedded issuer; remote packages are installed as single-use remote delivery records and verified by Go. `ChannelContract.swift` rejects argument maps with any other key, so no call carries a trust input. `BarometerClient` in `BarometerBinding.swift` gains `installRemoteTask`, `cancelRun`, `setProxy` and `clearProxy`. XCTests in `example/ios/RunnerTests` cover the argument validation, the error-code filter, the embedded issuer and the call routing through the facade; CI does not run them. No Dart API or channel contract change.
- Dart API and Android method channel: `BarometerClient` with `initialize`, `admitTask`, `startRun`, `runState`, `cancelRun`, `nextBundle`, `acknowledgeBundle`, `setProxy`, `clearProxy`, `clearMeasurementData` and `close`; the task sources `embeddedTask(name)` and `installRemoteTask(signedPackage)`; opaque `TaskHandle` and `RunHandle`; `Bundle` with the exact stored bytes; and `BarometerException(code)` carrying the facade's code. Construction does no work; the Android handler creates the record store and facade client at `initialize`, closes them at `close` and runs every facade call on a worker thread. Native code reads embedded tasks from the asset `barometer/tasks/<name>.json` and installs them with the trusted local document's embedded issuer, its one keyless issuer; remote packages are installed as single-use remote delivery records and verified by Go. No call carries a trust input, and the handler rejects argument maps with any other key. The README documents the channel contract. Dart unit tests, Kotlin host tests of the argument validation and instrumented channel tests cover it; CI now runs the Dart and Kotlin host tests. The iOS side of the channel is not wired yet.
- Apple capability and network adapters (DEV-729): Swift backends of the facade `Clock` (`Date()` used as trusted time when positive, otherwise unavailable with no fallback; manual time cannot be detected on iOS, which is weaker than the Android check and is recorded as a known limitation), `Consent` (always `absent`), `Device` (coarse battery and charging from `UIDevice`), `TimeZone` (IANA identifier), basic `Network` (`NWPathMonitor` type and IPv4 and IPv6 availability with an access-network generation and a single-shot change watch; VPN, validation and captive portal stay `unknown`) and `SystemResolver` (`getaddrinfo` bounded by the deadline). `BarometerBinding.newClient(store:trust:)` assembles them with the state store and returns a `BarometerClient`, and `TrustDocument` reads the `barometer-trust/1` document from the bundle resource `barometer/trust.json`. XCTests in `example/ios/RunnerTests` run TCP-01 and DNS-01 through the facade; [the Apple validation record](docs/apple-validation.md) lists the simulators and the device (DEV-730) that ran them and the trust-store check. No Dart API change and no support claim.
- Apple state-store backend (DEV-728): `RecordStore.swift`, the Swift backend of the facade `Records` callback, with the Android store's semantics. Records are files under the application's Application Support directory, excluded from backup, with atomic replacement, per-call deadlines, arrival-order execution that keeps abandoned writes behind later deletes and close, refusal of other puts while a clearing marker is stored, one owner per scope across processes and no work on the main thread. `BarometerBinding.records(_:)` adapts it to `BarometermobileRecordsProtocol` and returns the facade's absent value for a missing key. XCTests in `example/ios/RunnerTests` and `scripts/ios-record-store-kill-test.sh` cover it on the simulator. No Dart API change.
- Android capability and network adapters (DEV-725): Kotlin backends of the facade `Clock` (wall clock trusted only while automatic time is on, otherwise unavailable), `Consent` (always `absent` until a host consent source exists), `Device` (coarse battery and charging), `TimeZone` (IANA identifier), basic `Network` (coarse type and IPv4 and IPv6 availability with an access-network generation and a single-shot change watch; VPN, validation and captive portal stay `unknown`) and `SystemResolver` (`InetAddress` lookup bounded by the deadline). `BarometerBinding.newClient` assembles them with the state store, and `TrustDocument` reads the `barometer-trust/1` document from the application asset `barometer/trust.json`. The plugin manifest now requests `ACCESS_NETWORK_STATE`, which merges into host applications. Instrumented tests run TCP-01 and DNS-01 through the facade; [the Android validation record](docs/android-validation.md) lists the emulators and device that ran them. No Dart API change and no support claim.
- Android state-store backend (DEV-724): `RecordStore`, the Kotlin backend of the facade `Records` callback, stores one storage scope's records as files under the application's no-backup directory with atomic replacement, per-call deadlines, arrival-order execution that keeps abandoned writes behind later deletes and close, refusal of other puts while a clearing marker is stored, one owner per scope and no work on the UI thread. JVM unit tests and instrumented tests cover it. No Dart API change.
- Repository skeleton (DEV-715): a Flutter plugin for Android and iOS with no Dart API, an example application, a script that builds the native Barometer library from a pinned `barometer-go` commit, and CI that builds the example on both platforms. Android minSdk 21 and compileSdk 35, iOS 15.0, Dart `^3.8.1`. Nothing is published.

### Changed

- The Android `RecordStore` keeps a 64 KiB zero-filled reserve file, `clearing.reserve`, in each storage scope's directory. A put of a clearing marker deletes it first, so `clearMeasurementData` can store its marker and complete on a full disk, where it previously failed with `clearing_incomplete`; the reserve is allocated again when no marker is stored or the scope is opened, if space allows.
- `scripts/barometer-go.revision` pins `barometer-go` `7f5d7de7ada4709c1b2a4fdebbb4fb9b013ef918` (the merge of barometer-go PR #126), which adds the platform suspension signal to the `Network` port (`NewAccessState` takes a final `suspended` argument) and the trusted local policy restriction inputs. The Swift network callback passes `"unknown"` for suspension. Embedded tasks without `not_after` are now admitted only when the trusted local document lists them in `release_reviewed_tasks`, so the example's trusted local document lists its two one-time tasks by issuer and SHA-256 digest, which the Android Gradle task and the iOS build phase fill from the task bytes they write. No Dart API or channel contract change.
- Advance the `barometer-go` pin to `d7a5440ef35accc89a16a3074c586fa3d9f0308a`, which on Android uses the updatable or system CA store as trust roots instead of Go's default loading, never user-installed CAs, and rejects TLS-dependent tasks when no store loads. No Kotlin, Swift, Dart API or channel contract change.
- CI runs only formatting, analysis and the Dart tests on pull requests and pushes to `main`. The Android and iOS example builds, the Kotlin host tests, the emulator and simulator integration tests and the umbrella-mode builds move unchanged to the new `Device build` workflow, which is started manually from the Actions tab. No plugin, Dart API or channel contract change.
- `scripts/barometer-go.revision` pins `barometer-go` `5bc13351fbfd36090c7e24122781fd4700d46491` (the merge of barometer-go PR #120), which admits an embedded one-time task without `not_after`: repeat mode `none` and `max_runs` 1. The example's TCP-01 and DNS-01 tasks now declare exactly that and no longer carry a build-time `not_after`; `__EXPIRES_AT__` remains only for the target registration expiry in the trusted local document, so an example build is still usable for six days. The README states the host obligations of the exception: release review fixes such a task to one run, and the host does not persist it across application updates. No Kotlin, Swift, Dart API or channel contract change.
- CI builds with Flutter 3.47.8 instead of 3.47.6. Flutter 3.47.8 carries Dart security advisory GHSA-frr6-h895-5pxp: Dart 3.13.7 updates BoringSSL to block compromised eMudhra intermediate CA certificates and makes `dart:io` on Android 14 and later use the updatable Conscrypt root certificate store. The default Android application minSdk stays 24, so the README's minSdk statement is unchanged apart from the version. The `pubspec.yaml` SDK constraints are unchanged.
- `scripts/barometer-go.revision` pins `barometer-go` `c49695c9406d64d34d247de827ae2b0343634640` (barometer-go PR #116). The facade's `Records.Get` now reports a known-absent key with the non-nil `newAbsentRecordValue()`, because Swift cannot return nil from the generated throwing method, and treats a nil return as unavailable. The `Records` adapter in `BarometerBinding.kt` returns the absent value for a key `RecordStore` does not hold, and `RecordStoreDeviceTest` expects it. `RecordStore` itself, Swift and Dart are unchanged.
- `scripts/barometer-go.revision` pins `barometer-go` `8f8d7c4a01159e654f58bd7d340cd6e4533069f2`. With it the facade hands `Records` and `LinkageKeyStore` callbacks to native code in the order Go issues them and never hands over a call past its deadline, so a write abandoned before a clear can no longer reach `RecordStore` after it; `StartRun` also fails closed once its lifecycle deadline has passed. The README and `RecordStore` documentation now say which side guarantees the order. No Kotlin, Swift or Dart behavior changes.
- `scripts/barometer-go.revision` pins `barometer-go` `52789565c85f9d14d7b2ce1d5e42f85b11cea753`, the merge of the `barometermobile` gomobile facade (DEV-723). The native library now exposes only the facade, so `BarometerBinding.kt` and `BarometerBinding.swift` name `barometermobile.Client` and `BarometermobileClient` (DEV-724).
